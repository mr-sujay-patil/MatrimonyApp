# Coding Standards

This document establishes the mandatory engineering standards for the Matrimony Platform. All software development, including code written by human developers and generated by AI agents, must strictly adhere to these rules.

Every rule specified in this document must be programmatically or manually verifiable during pull request reviews. Subjective guidelines and optional recommendations are forbidden; conventions must be followed as strict rules.

---

## 1. Engineering Principles

The platform is built on five core engineering principles:

*   **Clean Architecture & Domain-Driven Design (DDD)**: Source code must be partitioned into strict layers: Domain, Application, Infrastructure, and Interfaces. Dependencies must only point inward toward the Domain. Business logic must live in Domain aggregates, entities, and domain services.
*   **Fail-Fast**: Validate inputs, payloads, and state transitions at the outermost boundary (interfaces/adapters). Raise explicit, typed exceptions immediately rather than permitting invalid state to propagate.
*   **Immutability First**: Use immutable data structures, readonly properties, and pure functions by default. Only permit mutations where performance profiling proves it necessary.
*   **Test-Driven Design (TDD)**: Test suite execution must guide the design of boundaries and interfaces. Implement tests alongside implementation code, mocking external interfaces, not internal domain models.
*   **Trunk-Based Development**: Integrate all modifications back to the `main` branch daily. All merges must occur through short-lived pull requests (< 400 lines of code) that pass automated CI checks.

## 2. Repository Standards

The Matrimony Platform is organized as a single monorepo.

### Monorepo Structure

The repository must follow this layout:

```
/
├── apps/
│   ├── frontend/             # React SPA (Vite + TS)
│   └── admin-portal/         # React Admin Portal (Vite + TS)
├── services/
│   ├── auth/                 # Auth microservice
│   ├── profile/              # Profile microservice
│   ├── match/                # Match matching microservice
│   ├── search/               # Search indexing microservice
│   ├── chat/                 # Chat microservice
│   ├── recommendation/       # Recommendation microservice
│   └── notification/         # Notification microservice
├── packages/
│   ├── shared-events/        # Shared event schemas (TS)
│   ├── shared-errors/        # Shared error envelope models
│   └── shared-logger/        # Structured JSON logging package
├── infra/
│   ├── docker/               # Local development compose and Dockerfiles
│   └── k8s/                  # Kubernetes manifest templates
└── package.json              # Monorepo configuration (npm workspaces)
```

### Microservice Scaffold Layout

Every backend microservice under `services/` must follow this structure:

```
services/{service-name}/
├── src/
│   ├── domain/               # Domain Model (Aggregates, Entities, Value Objects, Domain Events, Ports)
│   ├── application/          # Use Cases, Command/Query Handlers, DTO mapping definitions
│   ├── infrastructure/       # Database Adapters, Message Broker Adapters, External Clients
│   ├── interfaces/           # Express/Go Controllers, HTTP Routers, Middleware, Event Consumers
│   └── app.ts                # Dependency Injection composition root and app startup
├── tests/
│   ├── unit/                 # Domain and application layer tests
│   ├── integration/          # Infrastructure adapter tests (with Testcontainers)
│   └── contract/             # Pact API contract files
├── tsconfig.json
└── package.json
```

### Shared Libraries Policy

*   **DRY vs. Decoupling**: Do not create shared libraries for business logic. Shared packages must only contain cross-cutting concerns (e.g., logging formats, standard error envelopes, core types, or security middleware).
*   **Version Pinning**: All shared local packages must be version-linked via monorepo workspace references (e.g., `"@matrimony/shared-events": "workspace:*"`).

## 3. Backend Standards

These standards apply to all backend microservices, targeting Node.js (TypeScript) and Go (where performance-critical).

### Naming Conventions

*   **Classes**: Must use `PascalCase` (e.g., `RegisterUserUseCase`).
*   **Interfaces**: Must use `PascalCase`. Do not use an `I` prefix. Interfaces representing ports must be named after their role, ending with `Repository` or `Port` (e.g., `UserRepository`, `PaymentGatewayPort`).
*   **Methods & Functions**: Must use `camelCase` (e.g., `findActiveProfilesByCriteria`).
*   **Variables & Parameters**: Must use `camelCase` (e.g., `profileId`).
*   **Constants**: Must use `SCREAMING_SNAKE_CASE` (e.g., `MAX_FAILED_LOGIN_ATTEMPTS`).
*   **Enums**: Both the Enum name and its members must use `PascalCase` (e.g., `ProfileStatus.PendingVerification`).

### Clean Code Rules

*   **Method Length**: No function or method may exceed **40 lines of code** (excluding comments and line wraps). If a function exceeds this limit, it must be refactored into smaller utility functions or helper classes.
*   **Single Responsibility**: A class must have only one reason to change. Use cases must execute exactly one business operation (e.g., one Command handler per use case).
*   **Dependency Injection (DI)**: Classes must never instantiate their dependencies using `new`. All dependencies must be injected via constructors (Constructor Injection).
*   **Null Handling**:
    *   Functions must never return `null` or `undefined` to indicate an empty result or error.
    *   Use an `Option<T>` / `Maybe<T>` pattern, or throw a explicit `NotFoundError` when a single requested item is missing.
    *   Empty lists/arrays must be returned as an empty array `[]`, never as `null`.
*   **Error Handling**:
    *   Never use generic `Error` or `Exception` classes. All thrown errors must inherit from a service-specific base class that extends `ApplicationError`.
    *   All errors must specify a unique, SCREAMING_SNAKE_CASE error code (e.g., `PROFILE_ALREADY_VERIFIED`).
    *   Never catch errors and discard them (`catch (e) {}` with no action is forbidden).
*   **Logging Standards**:
    *   All logs must be output to `stdout` in structured JSON format.
    *   Every log entry must include: `timestamp` (ISO 8601 UTC), `level`, `message`, `service`, `correlationId` (for request tracing), and optional context metadata.
    *   Never log raw parameters containing PII (emails, phone numbers, names, or addresses). Wrap these fields in masking filters or exclude them entirely.

## 4. Frontend Standards

These standards apply to the React 18 frontend built with Vite, TypeScript, and TailwindCSS.

### Component Structure

*   **Single File Components**: Every component must be placed in its own file named `PascalCase.tsx`.
*   **Directory Structure**: Group components by domain context.
    ```
    frontend/src/
    ├── components/           # Shared generic UI components (Buttons, Inputs, Modals)
    ├── features/             # Domain-specific features
    │   ├── profile/
    │   │   ├── components/   # Profile-specific UI components
    │   │   ├── hooks/        # Profile-specific custom hooks
    │   │   └── index.ts      # Public API for the profile feature
    └── store/                # Global Zustand stores
    ```
*   **Typing Props**: All component props must be explicitly typed using TypeScript `interface` declarations. Never use `any`.

### State Management

*   **Zustand (Client State)**: Use Zustand for global UI state only (e.g., theme toggle, sidebar open state, active navigation tabs).
    *   Stores must be modular (e.g., `useUiStore`, `useAuthStore`).
    *   Never store API data inside Zustand.
*   **React Query (Server State)**: Use React Query (TanStack Query) for all remote data fetching, caching, synchronization, and mutations.
    *   Query keys must be structured as arrays of strings/objects following a deterministic pattern (e.g., `['profiles', profileId, 'preferences']`).

### Hooks Conventions

*   All custom hooks must begin with the `use` prefix (e.g., `useProfileDetails`).
*   Hooks must contain only logic. They must never return React Elements (JSX).

### Styling Conventions

*   Use Neumorphism (Soft UI) styling as defined in the design spec.
*   All styles must be defined using TailwindCSS utility classes or CSS variables in `index.css`.
*   Inline styles (`style={{ ... }}`) are forbidden except for dynamically calculated layout properties (e.g., drag-and-drop coordinates or progress percentages).

### Form Handling & Validation

*   Use React Hook Form for all forms.
*   All forms must be validated on the client side using a matching Zod schema. Schema definitions must be co-located with the form component file.

## 5. API Standards

All REST API endpoints must conform to the following specifications:

### Naming & Routing

*   Paths must use lowercase hyphenated names for resources: `/api/v1/profile/user-profiles`.
*   Routes must represent a hierarchy: `/api/v1/profile/user-profiles/{profileId}/photos`.

### Payload Conventions

*   **Requests**: Must use `camelCase` for JSON keys (e.g., `annualIncomeInr`).
*   **Responses**: Must match the standard envelope layout:
    ```json
    {
      "success": true,
      "data": {},
      "meta": {
        "timestamp": "2026-06-21T14:30:00Z",
        "correlationId": "01H2PJX2Z..."
      }
    }
    ```
*   **DTOs**: Every request and response payload must have a dedicated DTO (Data Transfer Object) class or interface named `{Action}{Resource}RequestDto` or `{Resource}ResponseDto`.

### Pagination

*   All endpoints returning lists must implement pagination.
*   Use **Page-based pagination** (query parameters: `page`, `limit`) for static records, search indices, and tabular list views.
*   Use **Cursor-based pagination** (query parameters: `cursor`, `limit`) for dynamic feeds, chats, and timeline notifications.

### Error Envelope

All HTTP non-2xx responses must return this structured format:

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "The provided input parameters are invalid.",
    "details": [
      {
        "field": "email",
        "issue": "Invalid email address format."
      }
    ],
    "correlationId": "01H2PJX2Z...",
    "timestamp": "2026-06-21T14:30:00Z"
  }
}
```

## 6. Database Standards

These standards govern the schema design, naming, migrations, and operations on PostgreSQL.

### Table & Column Naming

*   **Tables**: Must be lowercase, plural, snake_case (e.g., `partner_preferences`).
*   **Columns**: Must be lowercase, snake_case (e.g., `annual_income_inr`).
*   **Primary Keys**: Must be named `id` and be of type `CHAR(26)` containing a ULID.
*   **Foreign Keys**: Must be named `{referenced_singular}_id` (e.g., `user_profile_id`).

### Database Constraints

*   **Nullability**: Every column must be explicitly declared as `NOT NULL` unless the value is truly optional.
*   **Foreign Key Constraints**: All foreign keys must enforce relational integrity. Cascading deletes (`ON DELETE CASCADE`) are forbidden for primary business aggregates.
*   **Index Naming**:
    *   Index: `idx_{table_name}_{column_names}`
    *   Unique Constraint: `uq_{table_name}_{column_names}`

### Audit Fields

Every persistent table in PostgreSQL must include the following audit fields:

```sql
created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
version INT NOT NULL DEFAULT 1
```

*   All timestamps must use `TIMESTAMPTZ`. Never use local timezone formats.
*   An `ON UPDATE` trigger must automatically increment `version` and set `updated_at = CURRENT_TIMESTAMP`.

### Soft Deletes

*   Do not delete records from primary transactional tables. Use a nullable timestamp column named `deleted_at TIMESTAMPTZ`.
*   Queries must filter out deleted records: `WHERE deleted_at IS NULL`.

### Migrations

*   All database changes must be executed via migration files managed by a tool like Flyway or Golang-migrate.
*   Migration files must be named using this pattern: `V{YYYYMMDDHHMM}__description.sql` (e.g., `V202606212000__create_user_profiles.sql`).
*   DDL changes must be zero-downtime compatible:
    *   Adding an index must use `CREATE INDEX CONCURRENTLY` in PostgreSQL.
    *   Adding a non-nullable column must be done in three steps: add as nullable, backfill data, then alter column to set `NOT NULL`.

## 7. Event Standards

Events facilitate communication across microservices over RabbitMQ.

### Naming Conventions

*   **Event Names**: Must be past-tense, PascalCase representing a business fact (e.g., `UserProfileCompleted`, `PremiumSubscriptionActivated`).
*   **Topics/Routing Keys**: Must use lowercase snake_case structured as `{originating_service}.{domain_entity}.{event_action}` (e.g., `profile.user_profile.completed`).

### Event Payload Structure

All events must adhere to this standard wrapper envelope:

```json
{
  "eventId": "01H2PJX2Z...",
  "eventType": "UserProfileCompleted",
  "source": "profile-service",
  "version": "1.0",
  "occurredAt": "2026-06-21T14:30:00Z",
  "correlationId": "01H2PJX2Z...",
  "data": {
    "profileId": "01H2PJX3Y...",
    "userId": "01H2PJX4X..."
  }
}
```

### Idempotency & Versioning

*   **Consumer Idempotency**: Consumers must track processed `eventId` values inside an idempotency table or Redis store. Transactions must be rolled back if the event has been processed previously.
*   **Versioning**: Event schema changes must be backward-compatible (non-breaking additions only). If breaking changes are required, increment the payload version field (e.g., `"version": "2.0"`) and publish to a new topic path.

## 8. Testing Standards

Quality gates are enforced at each pipeline stage.

### Coverage Expectations

*   **Unit & Integration Tests**: Every microservice must achieve at least **80% statement and branch coverage**. Pull requests violating this will be blocked.

### Test Structure & Naming

*   Tests must follow the AAA pattern (Arrange, Act, Assert).
*   Test suites must use descriptive blocks:
    ```typescript
    describe('RegisterUserUseCase', () => {
      it('should throw validation error when email is malformed', async () => {
        // Arrange, Act, Assert
      });
    });
    ```

### Mocking Rules

*   Only mock adapters, network interfaces, and infrastructure systems at service boundaries (e.g., DB drivers, external API HTTP calls, RabbitMQ client wrappers).
*   Never mock internal domain models, aggregates, entity instances, or pure business rule components.

## 9. Security Standards

### Secrets Management

*   Secrets, API keys, password salts, and private keys must never be hardcoded or checked into git repositories.
*   Use environment variables for configurations, injected via Kubernetes Secrets or Cloud Secret Managers at runtime.

### JWT Handling

*   JWT payloads must never contain sensitive PII.
*   Access tokens must have an expiration window of exactly **15 minutes**.
*   Refresh tokens must be configured with HttpOnly, Secure, and SameSite=Strict cookie flags with a **7-day** maximum duration.

### PII Protection

*   Encrypt sensitive fields (e.g., `phone_number`, `annual_income_inr`, `tax_id`) in transit using TLS 1.3 and at rest in PostgreSQL/MongoDB using AES-256 transparent database encryption.

## 10. Pull Request Standards

### PR Constraints

*   **PR Size**: No pull request should exceed **400 lines of code** (excluding tests, auto-generated files, and yarn/npm lock files). Large features must be split into multiple atomic PRs.
*   **Story Tracking**: The PR title must start with the backlog issue ID (e.g., `[STORY-005] Refactor match filtering logic`).

### Definition of Done (DoD)

Before any PR can be merged:

1. All automated tests in the CI pipeline must pass successfully.
2. Code coverage must meet the 80% threshold.
3. No security alerts (e.g., npm audit vulnerabilities) can be introduced.
4. Linter checks (ESLint, Prettier, or Go fmt) must pass with zero warnings.
5. At least one human code owner must review and approve the changes.

## 11. AI Agent Standards

These rules govern the actions of AI coding assistants and autonomous code generation workflows.

### Forbidden Behaviors

*   **Do Not Mutate Approved Architecture Artifacts**: AI agents must never modify documents in the root directory representing architecture design (e.g., `ADR.md`, `System Context Diagram.md`, `API Contract Specification.md`, `Database Design.md`) unless explicitly instructed by the user.
*   **No Unverified Dependencies**: Do not add new external library dependencies to `package.json` or `go.mod` without explicitly obtaining confirmation from the user.
*   **No Code Placeholders**: Never output commented code or stub statements like `// TODO: implement later` inside production files. All generated files must be fully implemented.
*   **Stop and Confirm on Ambiguity**: If a requirement is underspecified or contradicts existing architecture decisions, the agent must halt execution, list the discrepancy, and ask the user for clarification.

### Story-to-Code Workflow

*   Agents must reference the existing story IDs from `backlog.json` when generating files.
*   For scope changes or architecture adjustments, agents must propose a new backlog item first instead of changing codebase behaviors implicitly.
